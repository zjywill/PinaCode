# 同步 PinaCode 上游

合入上游修复，同时保持同步前 PinaCode 的产品行为。以当前分叉的代码、测试和维护者最新指示为准。历史提交可能记录过后来已替换的方案，例如桌面共享曾使用嵌入式 Tailscale 节点，后来改为通过宿主机网络共享。

## 建立比较基线

核对分支和远端。通常 `origin` 是 PinaCode，`upstream` 是 pingdotgg/t3code。记录同步前的 HEAD 为 `before`，检查暂存、未暂存和未跟踪文件。保护原有工作，并在同步后恢复其内容和暂存状态。若请求只是复查某次合并，直接以该合并的第一父提交和合并结果比较。

抓取目标上游分支，记录目标提交为 `incoming`。用 `git merge-base "$before" "$incoming"` 找到共同基点 `base`。结合 `git diff --find-renames "$base" "$before"` 和分叉第一父链上的提交，找出本地修复、删除、重命名和新增入口。这个步骤也覆盖本技能创建之后才出现的定制。

## 按产品行为解决冲突

- **品牌与并行安装。** 对照分叉现有拼写使用 PinaCode 或 Pina Code。检查网页标题和图标、桌面更新弹窗、手机预览与小组件、CLI 帮助及服务端会传到客户端的错误提示。核对命令 `pinacode`、默认端口 `4773`、`~/.pinacode`、`PINACODE_HOME`、生产包名 `app.pinacode.client`、链接协议及开发变体。涉及发布时检查图标、签名更新配置和更新来源仍指向分叉的发布渠道。
- **已移除功能。** 本地使用和直接配对无需 T3 账号，远程活动推送和移动通知设置入口已移除。检查新路由、设置搜索、CLI 子命令、后台注册和依赖有没有重新接通这些功能。保留 provider 自己的认证、直接配对、宿主机网络共享，以及分叉实际支持的通知用途。
- **行为定制与修复。** 上游改到同一功能时，对照分叉的调用路径和测试。已知交叉点包括 DimCode Alpha 安装渠道、首条消息前的推理档位发现、订阅额度展示、后台线程在设置中的隔离，以及 Antigravity 工具 schema 对数值字面量的处理。逐段合并，例如保留上游的更新检查逻辑，同时保留 DimCode 的 npm dist-tag。
- **兼容标识。** 遇到 `T3` 或 `t3` 先追踪用途。`t3_*` MCP 工具名、`@t3tools/*` 包、已发布的持久化键、旧版迁移名称和上游许可证署名各有消费者。批量替换会破坏兼容性。遇到上游改动指向已删除文件，检查它是否把同一功能搬到了新路径；若修复也适用于分叉保留的入口，把修复移植到该入口。

## 验证合并结果

1. 审查相对 `before` 的**完整合并差异**，包括 Git 自动合并的文件。合并已暂存时可用下列命令定位新增旧品牌文案，再按路径和用途判断。另查图标等二进制资源和间接导入的注册入口。

   ```sh
   git diff --cached -U0 "$before" -G 'T3 Code|T3Code|T3.code|t3code|T3CODE_HOME|3773|com\.t3tools|`t3 ' -- apps packages scripts
   ```

2. 将基点到分叉的删除和重命名清单与最终树比较，再查设置、导航、命令注册及后台启动路径。文件仍缺失，只能证明原路径没有恢复。确认替代入口的实际行为。
3. 对双方都改过的行为运行现有的针对性测试；跨包改动检查受影响端的类型。对用户可见的界面变更按仓库规则验证。检查最终 HEAD 的上游祖先关系和工作区状态。若检查失败，区分基线已有问题与本次回归，并报告实际验证范围。
4. 交付时概括同步到的上游版本、用户能感知的修复、保留下来的定制和原有工作区改动的去向。按本次请求决定是否推送或发布。

## 跟进同步 PR

在独立 worktree 中完成同步并按用户授权创建 PR 后，用 `pinacode_watch_pull_request` 登记 PR URL，设置 `until: "merged"`。如果主会话委派实现并负责跟进，由主会话登记并带上原独立会话的 `followUp` 关联。保留监听至合并、关闭或用户要求停止。启用合并清理时，PinaCode 会在确认合并后检查对应 worktree。
